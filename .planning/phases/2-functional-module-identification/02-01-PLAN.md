<task type="auto">
  <name>Tarea 1: Agrupar controladores por dominio funcional</name>
  <files>.planning/phases/2-functional-module-identification/MODULOS-CANDIDATOS.md</files>
  <action>
    Usa `mcp__project2context__query_classes` para obtener todos los controladores de cloud2.
    Analiza los nombres de los controladores e infiere el dominio funcional de cada uno basándote en su nombre y ruta de archivo.

    Dominios DCS esperados (pero verifica contra el código real):
    - Check-in / Pasajeros
    - Asientos (Seat Map)
    - Equipaje (Baggage)
    - Boarding / Gate
    - Carga / Loadsheet
    - Vuelo (Flight)
    - Documentación (APIS, Manifiesto)
    - PSS/GDS Integration
    - Autenticación / Usuarios
    - Aerolínea / Tenant Config
    - Aeropuerto / Airport Config
    - Administración / Reportes

    Crea MODULOS-CANDIDATOS.md con:
    1. Sección "## Módulos Candidatos Identificados" — tabla: | Módulo | Controladores | Justificación |
    2. Lista de controladores que no pudieron clasificarse en "## Controladores Sin Clasificar"

    Cita los nombres reales de los controladores — no inventes agrupaciones.
  </action>
  <verify>MODULOS-CANDIDATOS.md existe con tabla de módulos y controladores reales agrupados por dominio.</verify>
  <done>Controladores agrupados por dominio funcional con justificación basada en nombres reales.</done>
</task>

<task type="auto">
  <name>Tarea 2: Validar módulos candidatos con modelos y vistas</name>
  <files>.planning/phases/2-functional-module-identification/MODULOS-CANDIDATOS.md</files>
  <action>
    Para cada módulo candidato identificado en la Tarea 1:
    Usa `mcp__project2context__query_classes` para encontrar los modelos asociados al módulo.
    Usa `mcp__project2context__search_files` para encontrar las vistas (resources/views/) asociadas.

    Actualiza MODULOS-CANDIDATOS.md bajo "## Módulos Candidatos Identificados":
    Para cada módulo agrega:
    - Modelos asociados (nombre + tabla si disponible)
    - Subdirectorios de vistas asociados (ej: resources/views/checkin/)

    Si un modelo o vista aparece en múltiples módulos, marca como "COMPARTIDO" — esto es crítico para el análisis de acoplamiento.

    Registra solo asociaciones que puedas evidenciar con rutas reales de P2C.
  </action>
  <verify>Cada módulo en MODULOS-CANDIDATOS.md tiene al menos un modelo y/o vista asociado con rutas reales.</verify>
  <done>Módulos validados con modelos y vistas reales del codebase.</done>
</task>

<task type="auto">
  <name>Tarea 3: Identificar código compartido y transversal</name>
  <files>.planning/phases/2-functional-module-identification/MODULOS-CANDIDATOS.md</files>
  <action>
    Usa `mcp__project2context__query_classes` para identificar:
    - Helpers/Traits que son usados por múltiples módulos
    - Modelos base o abstractos compartidos
    - Servicios transversales (logging, notificaciones, auditoría)
    - Providers de Laravel que afectan a múltiples módulos

    Agrega sección "## Código Transversal y Compartido" en MODULOS-CANDIDATOS.md:
    - Lista de helpers/traits compartidos con lista de módulos que los usan
    - Lista de servicios transversales con descripción del impacto en la reescritura
    - Nota sobre cada elemento: "alta complejidad de extracción" o "fácilmente extraíble"

    Solo documenta lo que se puede verificar con P2C.
  </action>
  <verify>Sección "## Código Transversal y Compartido" con elementos reales que aparecen en múltiples módulos.</verify>
  <done>Código compartido identificado con impacto en la reescritura modular documentado.</done>
</task>
