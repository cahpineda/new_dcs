<task type="auto">
  <name>Tarea 2: Clasificar requisitos de auditoría por tipo y regulación</name>
  <files>.planning/phases/7-logging-auditing-strategy/LOGGING-AUDITORIA.md</files>
  <action>
    Clasificar los eventos de auditoría en 4 categorías con sus requisitos de retención y trazabilidad:

    **Categoría A — Regulatorio/Legal (no negociable)**
    Eventos que exige la regulación aeronáutica o de gobierno:
    - Envíos APIS/PNRGOV a autoridades migratorias → retención mínima legal por país
    - Movimientos de pasajeros en fronteras → obligatorio para todas las aerolíneas
    - Transacciones financieras → PCI-DSS (si aplica), retención fiscal

    **Categoría B — Operacional Crítico (SLA y reversibilidad)**
    Eventos que permiten reconstruir el estado del vuelo ante un incidente:
    - Toda emisión/anulación de boarding pass (quién abordó, quién no)
    - Check-in transactions (qué agente, qué pasajero, qué vuelo, timestamp)
    - Asignaciones de asiento (historial de cambios — doble asignación es un incidente crítico)
    - Aprobaciones de loadsheet (W&B firmado — responsabilidad legal)
    - Gate overrides (supervisor autorizó embarque de pasajero en lista de denegación)

    **Categoría C — Seguridad de acceso**
    Eventos de autenticación y autorización:
    - Login/logout de agentes con IP, estación, carrier
    - Acciones de administrador (cambio de configuración, override de regla)
    - Acceso fallido (intentos de acceso no autorizado)
    - Cambios de rol/permiso

    **Categoría D — Diagnóstico/Observabilidad**
    Eventos para debugging y monitoreo de salud del sistema:
    - Errores de integración (CUPPS timeout, SITA SOAP fault, APIS rejection)
    - Performance (latencia de operaciones críticas)
    - Colas de jobs (QueuedJobs — fallos y reintentos)
    - XCache/APCu misses (salud del autoloader)

    Documenta en LOGGING-AUDITORIA.md bajo "## Clasificación de Requisitos de Auditoría":
    Tabla por categoría con: evento, retención mínima, acceso permitido, inmutabilidad requerida.

    **Retenciones mínimas recomendadas para aviación:**
    - APIS/gobierno: según regulación de cada país (típico: 5-7 años)
    - Boarding/check-in: 24 meses operacional + archivo
    - Financiero: 5-7 años (fiscal)
    - Acceso/seguridad: 12-24 meses
    - Diagnóstico: 30-90 días rolling
  </action>

  <name>Tarea 3: Definir estrategia de logging/auditoría para el nuevo sistema</name>
  <files>.planning/phases/7-logging-auditing-strategy/LOGGING-AUDITORIA.md</files>
  <action>
    Diseñar la estrategia de logging/auditoría para el DCS reescrito. Documentar en "## Estrategia de Logging para el Sistema Reescrito":

    ### 3.1 Arquitectura de logging — dos capas

    **Capa 1 — Audit Log Inmutable (categorías A y B)**
    - Destino: tabla `audit_events` append-only (sin UPDATE/DELETE por diseño)
    - Schema mínimo: `(id, event_type, entity_type, entity_id, actor_id, carrier_key, station_id, payload_json, occurred_at, ingested_at)`
    - Propiedad clave: `occurred_at` viene del cliente, `ingested_at` es del servidor — detecta manipulación de timestamps
    - Escritura: síncrona para categoría A (si falla el audit log, falla la operación), asíncrona para B
    - PII: `payload_json` encriptado at-rest para datos de pasajero (nombre, documento, PNR)
    - Acceso: solo lectura para operaciones, lectura/escritura solo para compliance tool

    **Capa 2 — Observabilidad / Diagnóstico (categorías C y D)**
    - Destino: BigQuery (BigQuery ya existe via `BQHandler.php` — extender)
    - Logs estructurados en JSON con `tenant_id`, `correlation_id`, `service`, `severity`
    - Retención corta (30-90 días) con compactación automática
    - Acceso: equipo de operaciones, dashboards de monitoreo

    ### 3.2 Correlation ID — trazabilidad end-to-end

    Cada operación que cruza módulos DEBE propagarse un `correlation_id`:
    - Generado en el entry point (check-in, boarding, etc.)
    - Propagado en HTTP headers (`X-Correlation-Id`) entre servicios
    - Incluido en TODOS los audit events de la operación
    - Permite reconstruir el flujo completo: check-in → seat assignment → boarding pass → APIS submission

    Sin correlation ID no es posible auditar una operación multi-módulo (ej: investigar por qué un pasajero fue denegado en puerta).

    ### 3.3 Manejo de PII (Personally Identifiable Information)

    El DCS maneja PII sensible: nombre, pasaporte, fecha de nacimiento, PNR, datos de tarjeta.
    - PII en audit logs: solo el identificador (`passenger_key`, `pnr`) — no el dato raw
    - Para investigaciones que requieren PII: join contra tabla `passenger` con control de acceso separado
    - Logs de diagnóstico (categoría D): PII completamente excluida — solo IDs
    - Logs de integración APIS: retener payload completo en tabla separada con acceso restringido (regulatorio)

    ### 3.4 Estrategia por integración externa

    | Integración | Qué auditar | Dónde | Retención |
    |---|---|---|---|
    | APIS/Gobierno | Request completo + response + timestamp | Tabla `apis_submission_log` (append-only) | Legal por país |
    | SITA BaggageService | Tag ID, reconciliación result, flight | Audit log Capa 1 | 24 meses |
    | CUPPS/CUTE | Eventos de periférico, errores, reconexiones | Observabilidad Capa 2 | 30 días |
    | Pagos (Stripe/Worldline) | Transaction ID, monto, resultado — NO datos de tarjeta | Audit log Capa 1 | 5-7 años |
    | Auth service (JWT) | Emisión, expiración, revocación de tokens | Audit log Capa 1 (Cat. C) | 24 meses |

    ### 3.5 Audit log para el período de coexistencia (legacy + nuevo)

    Durante la migración por olas, el mismo vuelo puede tener operaciones en legacy PHP Y en handler nuevo. El correlation_id debe funcionar en ambos lados:
    - Legacy: inyectar `correlation_id` como parámetro de sesión PHP
    - Nuevo: propagar via HTTP header
    - Ambos escriben al mismo `audit_events` central
    - Esto permite auditar un incidente aunque la operación cruzó de legacy a nuevo en mitad del flujo
  </action>
